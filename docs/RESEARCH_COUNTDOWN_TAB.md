# 调研文档：倒数日 Tab（Research — 待用户确认，未实施）

> **状态**：🔬 调研阶段，仅方案分析，未动手实现。用户确认后再开工。
> **背景**：当前倒计时仅在侧栏显示一条文本（`GET /api/countdown` → `aggregator.build_countdown`），形式单一。用户提出希望有独立的「倒数日」Tab。

## 1. 现状盘点

| 项 | 现状 |
|---|---|
| 数据源 | `重要日期`（important）图层事件，`extra_json.offset==0` 取当天实事件 |
| 现有接口 | `GET /api/countdown` 返回 `{"text": "距离「和姐姐在一起 400 天」还有 5 天"}` |
| 前端展示 | `Sidebar.tsx` 底部固定区域渲染单条文本 |
| 语义 | 只显示**最近一个**重要日期（upcoming 里 date 距今天最近的）；无 past 展示分支（已过则显示「已过 N 天」） |

## 2. 用户诉求拆解（推测 + 需确认）

用户原话方向：「倒数日 tab」。结合现有 400 天纪念日倒计时场景，合理形态：

- **独立顶级 Tab「倒数日」**（与「日历 / 待办」并列），进入后展示**全部**重要日期列表，而非仅最近一条
- 每行：标题 + 剩余天数（`还有 N 天` / `已过 N 天` / `就是今天`）+ 日期 + 来源图层色点
- 排序：距离今天最近的在最前；可选「只显示未过期」
- 允许「+ 新建倒数日」：本质上就是往 important 图层写一条事件（`POST /api/events`）

## 3. 需要用户确认的分叉

| # | 问题 | 选项 A | 选项 B |
|---|---|---|---|
| 1 | 倒数日数据源 | 复用 important 图层全部事件（零新表） | 独立 `countdown` 表（可设名称/日期/重复规则，与图层解耦） |
| 2 | 形态 | 顶级 Tab（与日历/待办并列） | 侧栏内展开为列表（改动小） |
| 3 | 是否支持「重复」 | 单次日期即可 | 每年重复（纪念日场景，用 offset 系列事件） |
| 4 | 编辑入口 | 跳转重要日期图层新建事件 | Tab 内独立新建/编辑表单 |

## 4. 技术路径（若选 A1+B1：零新表，最省）

- **后端**：`GET /api/countdown/list` → 复用 `db.fetch_events_between(conn, today-365, today+365, layer_ids=[IMPORTANT])`，过滤 `offset==0`，按 `abs(date-today)` 排序，返回数组 `[{title, date, days_left, is_today, passed}]`；保留原 `/countdown` 单条接口给侧栏用。
- **前端**：
  - `TopBar` 加第三个顶级 tab「倒数日」；`App.tsx` `topTab` 类型扩展为 `'calendar'|'todo'|'countdown'`。
  - 新建 `CountdownView.tsx`：列表 + 排序 + 过期置灰；行点击 → 打开重要日期事件编辑（复用 EventEditor）。
  - `Sidebar` 的倒计时保留（或改为「最近 3 条」）。
- **数据量**：events 表仅几百行，接口无性能压力。

## 5. 风险与注意事项

- 重要日期图层若被用户**禁用**，倒数日 Tab 应仍显示（统计口径与图层开关解耦）——建议 `/countdown/list` 不依赖图层 enabled 状态。
- offset 系列事件（比如「400 天」可能存为 offset 事件链）需统一只取 offset==0 的主事件，避免重复。
- 若选 B1（独立表），需要迁移现有重要日期数据 + 新 CRUD，工作量约多半天。

## 6. 结论

**推荐 A1 + B1（复用 important 图层 + 顶级 Tab）**：改动集中在 `routes.py` 加一个 list 接口 + 前端一个新 View + TopBar 一个 tab，约 2-3 小时工作量，且与现有「重要日期」编辑流程天然打通。是否开工等用户确认。
