## 1. 任务栏图标"隐身"（已确认 · **2026-11-26 已修**）

### 事实

```
icons/icon.png        512×512   不透明像素 68%   不透明区平均色 RGB (0, 0, 0)
icons/128x128.png     128×128   不透明像素 71%   平均色 (0, 0, 0)
icons/32x32.png        32×32    不透明像素 83%   平均色 (0, 0, 0)
四角像素均为 (0,0,0,0)  →  透明底
```

不是"偏暗"，是**纯黑 #000**。而且尺寸越小不透明占比越高（68% → 83%），说明
字形在小尺寸下几乎铺满画布，黑块感更强。

### 根因

图标 = 黑色字形 + 全透明底。任务栏是深色（Win11 深色模式下接近 #202020），
黑字形直接融进去；因为没有底板，连"这里有个应用"的轮廓都没有。

不是 Windows 的问题，是我们的图标少了一层底。

### 建议修法

给图标加**圆角矩形底板**，字形反白（或深色底 + 浅色字形），类似 VS Code / Notion /
Linear 的做法。关键点：

- 底板要占满画布（或留 8%~10% 透明边距），圆角半径约画布 22%
- 32×32 与 16×16 必须单独看：细节要减到只剩主体轮廓，否则糊成一团黑
- 全套尺寸由一张 1024×1024 源图生成：`npx tauri icon src-tauri/icons/source.png`
- `icon.ico` 要包含 16/24/32/48/64/128/256 多档，否则资源管理器和小图标场景会取错

顺手一起做：**如果以后做提醒要上托盘，托盘图标也得是同一套**（托盘图标同样在深色
任务栏里，且通常只有 16×16，比应用图标更考验简化程度）。

### 已落地

- `scripts/gen_app_icon.py`：白底圆角矩形（3.5% 留白、22.5% 圆角）+ 沿用原字形 alpha
- 小尺寸（16/24/32/48）单独画简化版：**保留顶部两个挂环**——没有挂环，16~32px
  看起来完全像一张「文档」；内部方块按 16→1 个、24→2 个、32→4 个递减
- `icon.ico` 逐档渲染后再手工编码（`>=256` 用 PNG、小档用 DIB）。PIL 的 `save(sizes=...)`
  是从单张图缩放，16/32 档会拿到「真字形缩成一坨」，等于白做
- 验证图：`docs/shots/icon-taskbar-preview.png`（深浅任务栏对比）、
  `docs/shots/icon-ico-tiers.png`（ico 各档实际内容）

### 验收

- Win11 深色任务栏：图标有清晰轮廓，不隐身
- Win11 浅色任务栏：不刺眼
- 任务视图 / Alt+Tab：缩略图角标可辨
- 16×16（资源管理器"小图标"视图）：能看出是日历，不是黑方块

## 2. 今日视图里右栏不收回（已确认 · **2026-11-26 已修**）

用户描述：「点掉这个任务以后，右侧边栏不会正常缩回去」。

代码里确实**有两个**会导致这个现象的路径，它们的修法不同。

### 成因 A：勾选完成后，数据还在，所以抽屉认为"还有东西可看"

`frontend/src/components/TodoView.tsx:171`

```tsx
const selectedTodo = useMemo(
  () => findTodoById([incomplete, completed, todayDone], selectedTodoId),
  [incomplete, completed, todayDone, selectedTodoId],
)
```

`frontend/src/components/TodoView.tsx:670`

```tsx
<RightDrawer open={!!selectedTodo || selectedTodoId === '__NEW__'}>
```

勾选完成 → 任务从 `groups`（未完成）消失，但立即出现在 `todayDone` 里
（`completed_at` 是今天，正好命中今日完成的查询）。于是 `findTodoById` 依然找得到，
`selectedTodo` 依然 truthy，`open` 保持 true，抽屉不收。

而 176-184 行那段兜底 effect 只在**彻底找不到**时才清空：

```tsx
useEffect(() => {
  if (!selectedTodoId || selectedTodoId === '__NEW__' || selectedTodo) return
  if (detailDataReady) setSelectedTodoId(null)
}, [selectedTodoId, selectedTodo, detailDataReady])
```

勾完成这条路径永远不会"找不到"，所以 effect 不触发。

**修法**：在 `handleToggle` 里加一条——如果被勾掉的正是当前选中项且 `done === true`，
顺手 `setSelectedTodoId(null)`。语义最直白，也不会误伤"完成后还想继续看详情"的
其他视图（只在这条路径清）。

若希望更通用，可把 effect 条件扩展为「当前视图已不再展示这条」，但这需要给每个
视图定义"是否展示"的谓词，反而复杂。**建议就用 handleToggle。**

### 成因 B：点已选中的项不会取消选中

`frontend/src/components/todo/TodoTodayView.tsx:288`

```tsx
onClick={() => onSelect(td.id)}
```

`onSelect` 直接是 `setSelectedTodoId`（TodoView.tsx:560），**没有 toggle**。所以
"再点一次这条想关掉它"是无效的，用户只能点右侧关闭按钮或别处。

这个行为在 Matrix / Kanban / Stickies 三个视图里是一致的（都传 `setSelectedTodoId`），
属于全局交互约定，不是今日视图独有。

**修法**：`onSelect` 改成 toggle 语义（`id === selectedTodoId ? null : id`），
在 TodoView 里统一包一层，四个视图一起受益。

### 已落地

- `handleToggle` 开头：`if (done && selectedTodoId === todo.id) setSelectedTodoId(null)`
- 新增 `handleSelect`（`prev === id ? null : id`），替换四个视图 + 列表行的 7 处
  `setSelectedTodoId`，成因 B 一并解决
- 注意：`onOpenNotes` 里的 `setSelectedTodoId(t.id)` **不能**换，双击打开笔记是明确意图

### 建议

两条都修，一起验：

- [ ] 今日视图勾选完成 → 抽屉收回（成因 A）
- [ ] 任意视图再点已选中项 → 抽屉收回（成因 B）
- [ ] 回归：勾完成后立刻再点另一条 → 正常打开
- [ ] 回归：切标签筛选、切视图时抽屉不乱开乱关（现有 `detailDataReady` 逻辑别破坏）

## 3. 功能扩张的判断标准（先定标准，再谈功能）

「加功能会不会变臃肿」这个问题，我的看法是：**臃肿不来自功能数量，来自入口数量和
概念数量。**

- 提醒：不新增任何导航入口，只在已有待办上多一个字段。**属于隐形增强，不臃肿。**
- 专注：如果做成独立视图/独立 Tab，就是在左侧栏多一个入口、多一套概念
  （专注轮次、休息、统计）。**这才是臃肿的来源。**

所以判断一个功能要不要做，我建议用三条：

1. 它是否要求用户在**顶层导航**里多认一个东西？
2. 它是否引入一套用户必须先学会的**新概念**？
3. 它失败时（不响、不准、忘了开）用户会不会觉得"这应用不可靠"？

提醒在第 1、2 条都是"否"，但第 3 条风险极高——**提醒不准，比没有提醒更伤信任。**
专注在第 1 条就是"是"。

## 4. 待办提醒：该做，但不该在 3.0.0 做

### 现状盘点（这是关键，决定工作量）

| 东西 | 现状 |
|---|---|
| `todo.alarm_at` 字段 | **存在**（`tt_calendar/db.py:115`），但新端只透传（`sync/schema.py:40`） |
| 前端设置闹钟的 UI | **没有**（`core/types.ts:21` 只有一个类型声明） |
| 到点调度器 | **没有**（前后端都没有读 `alarm_at` 的地方） |
| Windows 通知能力 | **没有**（无 `tauri-plugin-notification`） |
| 托盘 / 开机自启 | **没有** |
| 现有 `ReminderBanner` | 是"每日固定时间在应用内提示今天有几件事"，**不是**逐条提醒 |

结论：这不是"接线"，是从零做。

### 三个绕不过去的硬约束

1. **AUMID**：Windows toast 需要 AppUserModelID。NSIS 安装版有开始菜单快捷方式，
   能弹；**便携版没有 AUMID，弹不出来**。要么给便携版做兜底（自绘窗口），要么
   明确"提醒仅安装版可用"。
2. **应用关了就没了**：要"关了也提醒"，必须托盘常驻 + 开机自启。而后端 sidecar
   是 Tauri 主进程 spawn 的，主进程一退，后端跟着退——调度器得挂在哪一侧，要重新设计。
3. **退出语义会变**：点 × 变成"收进托盘"是产品级决策。用户的第一反应往往是
   "我关不掉它"，这是差评高发区。必须在设置里给一个明确的开关。

### 为什么不该进 3.0.0

3.0.0 你准备拿去做宣传。宣传版的失败成本最高——一旦"提醒不响"成为第一印象，
后面修好了也很难挽回。而提醒恰恰是**最容易不响**的功能（权限、AUMID、睡眠唤醒、
免打扰、系统通知被关）。

建议节奏：

- **3.0.0（12/03）**：只修 bug + 打磨，把"稳定"这个词兑现
- **3.1.0（12 月中下旬）**：提醒。含托盘、开机自启、AUMID、稍后提醒、免打扰、
  已提醒状态持久化。作为独立一版，可以专心做透
- **3.1.x**：根据真实使用反馈修"提醒不响"的边角

### 3.1 的最小可用范围（供参考，不在本期）

- 待办详情里可设"某天某时提醒"
- 到点弹 Windows 通知（点击通知 → 打开该待办）
- 支持"稍后 10 分钟 / 今天不再提醒"
- 应用未启动时：托盘 + 自启（设置里可关）
- 便携版明确降级为"应用内提醒"

## 5. 专注模式：建议不做独立视图

### 我不太赞成"专门开一个专注视图"

理由不是"功能不好"，是**它会改变这个应用的品类**。

现在的 TT Calendar 是一个"看得清今天要做什么"的工具，心智模型是**清单 + 时间**。
专注模式的心智模型是**时间块 + 节奏**，需要用户先接受"一轮 25 分钟、中间休息 5 分钟"
这套规则。这是另一个品类（Forest、Focus To-Do 那一类）。

做完之后很可能的结局是：入口在那儿，用户点过两次，然后永远不再点。而左侧栏
永久多了一个需要解释的图标。

### 如果真要做，最轻的形态

**不做独立视图，只在待办详情里加一个「开始专注」按钮。**

- 点了之后进入一个全屏/半屏的极简倒计时，只显示这一条待办的标题
- 结束 → 勾选完成 → 回到清单
- 不引入"轮次""休息""统计"，就一个倒计时
- 依赖提醒能力（到点要响），所以**必须排在提醒之后**

这个形态的好处：它是"待办的一个动作"，不是"一个新的板块"，不增加顶层入口。

### 或者：做成插件

如果插件体系未来能挂载 UI（现在只能挂数据源），专注是绝佳的插件候选——
想用的人装，不想用的人一辈子看不到。这比内置更符合你"别臃肿"的顾虑。

**结论：专注推迟到 3.2，或做成插件。3.0.0 不做，3.1 也不做。**
